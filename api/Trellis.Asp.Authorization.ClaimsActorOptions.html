Remarks

Default behavior maps the OIDC standard sub claim to Id and the permissions claim to Permissions. Override the claim names to match your identity provider's token format.

Nested-claim mapping (ga-15). Both ActorIdClaim and PermissionsClaim are matched against the flat Type string only — no JSON-path or dotted traversal is performed. Two practical consequences:

  • Provider-prefixed claim names work as-is. Set the option to the full claim type the JWT handler emits, e.g. "http://schemas.microsoft.com/identity/claims/objectidentifier" (Entra oid) or "extension_role" (Entra External Identities custom attribute). Whatever the issuer/handler exposes via ClaimsIdentity.FindFirst(name) is what to put here.
  • JSON-object claims are not auto-flattened. When a JWT contains a nested object (e.g. { "app_metadata": { "roles": [ ... ] } }), the JWT handler stores the value as the raw JSON string under claim type "app_metadata". To project nested values into Permissions, subclass ClaimsActorProvider and override GetCurrentActorAsync(CancellationToken) to parse the JSON yourself, or use EntraActorProvider with a custom MapPermissions delegate which receives the full Claim sequence.
  • Multi-valued JWT claims are flattened automatically by JwtBearerHandler — a JSON array such as "permissions": [ "orders:read", "orders:write" ] arrives as multiple Claim instances of the same Type, which the default provider already aggregates via FindAll.

Properties

ActorIdClaim

The claim type used to resolve the actor's unique identifier. Defaults to "sub" (the RFC 7519 / OpenID Connect subject claim).

public string ActorIdClaim { get; set; }

Property Value

string

Remarks

Matched against Type verbatim; no dotted-path traversal. See the ClaimsActorOptions remarks for nested-claim guidance.

JwtBearer MapInboundClaims robustness. ASP.NET Core's JwtBearerOptions.MapInboundClaims defaults to true, which remaps RFC 7519 short claim names (e.g. "sub") onto WS-* long-form URNs (e.g. NameIdentifier) before they reach ClaimsIdentity. If the configured ActorIdClaim is not found literally, ClaimsActorProvider automatically falls back to the well-known short↔long counterpart from the JWT inbound claim-name map — covering the OAuth2 / OIDC / Microsoft-identity subset that consumers realistically configure as an actor id (sub/nameid ↔ NameIdentifier, oid ↔ the Microsoft objectidentifier URN, upn ↔ Upn, email ↔ Email, role/ roles ↔ Role, name/unique_name ↔ Name, etc.) — so the default configuration just-works with either MapInboundClaims = true or MapInboundClaims = false. The fallback emits a debug-level log entry when it fires. Recommended for new services: set MapInboundClaims = false on AddJwtBearer(...) so claim names round-trip with their RFC names.

PermissionsClaim

The claim type used to resolve the actor's permissions. Defaults to "permissions" (common convention in OIDC/JWT tokens).

public string PermissionsClaim { get; set; }

Property Value

string

Remarks

Matched against Type first; every matching claim contributes one entry. ClaimsActorProvider additionally queries the well-known short↔long counterpart from the JWT inbound claim-name map (role/ roles ↔ Role, etc.) and merges every match into a deduplicated set, so configurations like PermissionsClaim = "roles" or PermissionsClaim = ClaimTypes.Role just-work against either JwtBearerOptions.MapInboundClaims = true or false. The default "permissions" is not in the JWT inbound map, so its resolution remains literal-only. The fallback emits a debug-level log entry when it fires (i.e. when the configured name resolves nothing but a counterpart does). See the ClaimsActorOptions remarks for nested-claim guidance.

ValidateClaimShapeOnFirstUse

When true (the default), ClaimsActorProvider emits startup-diagnostics log entries the first time a configured claim fails to resolve into the shape the provider expects: the configured PermissionsClaim resolving to zero entries on an authenticated identity that carries other claims, or to a single value that parses as a JSON object or array; and the configured ActorIdClaim resolving to nothing on an authenticated identity. Every diagnostic is throttled to fire at most once per application lifetime — they surface the silent-403 and silent-401 footguns without producing log spam.

public bool ValidateClaimShapeOnFirstUse { get; set; }

Property Value

bool

Remarks

Why it exists. The most common silent-403 cause is a misconfigured PermissionsClaim against a nested-JSON identity-provider claim shape (Auth0 app_metadata.roles, Azure B2C extension_* custom attributes, some Okta token shapes). The configured flat claim name finds nothing literal, the known-name fallback table does not cover the consumer's IdP, and the provider returns an empty permissions set — every IAuthorize command then short-circuits to 403 with no signal pointing at the claim mapping.

The silent-401 variant is the same failure one step earlier: an unresolvable ActorIdClaim (typically a JwtBearerOptions.MapInboundClaims short↔long mismatch the fallback table does not cover) yields no actor at all, so a successfully authenticated caller is rejected with a bare 401.

Set to false only when the diagnostics duplicate an existing health-check or claim-validation pipeline.
