Remarks

Register as scoped in DI via AddClaimsActorProvider(IServiceCollection, Action<ClaimsActorOptions>?). Claim mapping is controlled by ClaimsActorOptions.

This provider assumes authentication has already occurred. It returns None when the request has no usable authenticated actor — no authenticated ClaimsIdentity, or the configured ActorIdClaim is missing from the authenticated identity — and the mediator authorization pipeline maps that to Error.AuthenticationRequired (HTTP 401). It throws InvalidOperationException only when invoked outside an HTTP request scope (no HttpContext); that is a configuration bug, not authentication state, and surfaces as HTTP 500.

Extending for nested or computed claims. The default mapping is flat (see the ClaimsActorOptions remarks). For provider-specific shapes — JSON-object claims, dotted paths, claims that need to be merged with an external store, or permissions derived from multiple raw claims — subclass this provider and override GetCurrentActorAsync(CancellationToken). The HttpContextAccessor and Options properties are protected precisely to support this. EntraActorProvider is a worked example.

logger ILogger<ClaimsActorProvider>

Optional logger; when supplied, emits a debug-level message naming the configured claim and the resolved counterpart each time the short↔long claim-name fallback resolves a value (either the actor id or one or more permission claims) that the configured literal claim name did not produce. Logging is suppressed when the configured claim resolves literally — the diagnostic targets the silent-401 / silent-403 footgun caused by JwtBearerOptions.MapInboundClaims = true; the merge case where both forms contribute is normal operation and would only add noise. The actor-id resolution emits at most one entry per request; the permissions resolution may emit one entry per resolved counterpart (forward long-form match, plus one per matched reverse short form) — typically zero or one, capped by the size of the well-known map.

public virtual IReadOnlyCollection<string> VaryByHeaders { get; }

Property Value

Remarks

Non-bearer auth. If your service authenticates with a different scheme (cookies, mTLS, forwarded headers, custom handler) the actor identity does NOT vary by Authorization and the default is wrong. Subclass ClaimsActorProvider and override VaryByHeaders to declare the correct header(s) — for example ["Cookie"] for cookie-backed auth. Failing to do so allows an intermediate HTTP cache to serve actor A's response to actor B's request when consumers call VaryForActor().

Stability contract. Overrides MUST return a collection whose contents do not change between requests. The framework re-reads VaryByHeaders on every response that opts into VaryForActor(); returning a mutable collection and mutating it between requests would emit inconsistent Vary headers across requests, breaking intermediate-cache partitioning. Return a frozen array literal (["Cookie"]) or a precomputed FrozenSet<T>; do not return a List<T> field that the subclass mutates over time.

From<T>(T?) wrapping the resolved Actor when an authenticated identity is present and the framework can identify the actor.

None when the request has no usable authenticated actor — typically the request lacks credentials, the authentication middleware did not produce an authenticated identity, or the authenticated identity is missing the claim needed to identify the actor. The Trellis mediator authorization pipeline maps this to Error.AuthenticationRequired (HTTP 401) per RFC 9110 §15.5.2. "No authenticated actor" is client-error state, not an exception — model it via the return value, not by throwing.

Exceptions

InvalidOperationException

Thrown only for genuine infrastructure or configuration failures — for example, the provider was invoked outside an HTTP request scope (missing HttpContext), a user-supplied mapping delegate threw, or an option is misconfigured. The mediator pipeline does not catch this case; it surfaces as Error.Unexpected (HTTP 500), which is correct because these are bugs rather than authentication state. Do not throw for "missing actor" — return None instead.

MaybeEmitClaimShapeDiagnostics(ClaimsIdentity, FrozenSet<string>)

Emits one-off startup diagnostics surfacing the two silent-403 footguns this provider cannot otherwise reach: (1) the configured PermissionsClaim resolved to zero entries on an authenticated identity that carries other claims, and (2) the configured claim resolved to a single value that parses as a JSON object or array. Remarks

The forward direction (configured short → long) has a single counterpart per short form. The reverse direction (configured long → short) iterates every short form that aliases to the long form (e.g., NameIdentifier ← {sub, nameid}; Name ← {name, unique_name}; Role ← {role, roles}) — picking only one short form would silently fail to resolve tokens that carry the alternate variant. protected so derived providers can use the same short↔long fallback when their own resolution path misses and they need to consult the flat claim shape as a backup.
