Remarks

Why this exists. An intermediate HTTP cache can only safely return a response to a request from actor B if it knows the response would have been the same for B as it was for A. The wire signal for that is the Vary response header naming the request headers the response varies on. Trellis owns the actor abstraction and therefore knows which request headers contribute to actor identity for the registered provider — Authorization for the JWT-bearer-backed ClaimsActorProvider / EntraActorProvider, the configured test header (X-Test-Actor by default) for DevelopmentActorProvider, and the wrapped provider's headers for CachingActorProvider. VaryForActor() emits those headers automatically when this interface is implemented; without the interface the builder method throws, fail-closed, rather than silently emit an incorrect or incomplete Vary header.

Implementation contract. The returned collection should name the HTTP request headers (case-insensitive, matching wire-shape conventions like Authorization / Cookie / X-Test-Actor) that contribute to actor resolution. Return an empty collection if and only if the provider's actor identity is derived from request data that cannot be cleanly named by a single HTTP header (e.g. mTLS) — in which case consumers should not be calling VaryForActor for those endpoints, and the right answer is usually Cache-Control: private, no-store.

Custom providers. A custom IActorProvider implementation that derives actor identity from non-bearer signals (cookies, mTLS, forwarded headers) must implement this interface explicitly to be usable with VaryForActor. The framework does not assume a default — guessing wrong here causes cache poisoning across actors.
