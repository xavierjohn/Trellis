Remarks

Atomicity. A reservation is claimed with a single CreateItem: Cosmos DB rejects a duplicate id within a partition with 409 Conflict, executed on the partition's primary replica, so exactly one concurrent caller can win. Every subsequent mutation — taking over a timed-out reservation, recording a response, releasing a slot — is an ETag-conditional replace or delete, so a caller whose view of the item is stale is rejected with 412 and retries rather than clobbering a newer state.

Session consistency is safe here. Reads on a Session-consistency account may be served by a replica that has not yet seen another instance's write, so the read following a 409 can return a stale item — or, briefly, 404. Neither can cause a double execution, because the store never grants a reservation on the strength of a read: it grants only when an atomic create succeeds, or when an ETag-conditional replace succeeds. A stale read simply produces a 412 or 404 on the follow-up write, and the operation retries. The worst observable effect is a spurious AlreadyInFlight, which the caller retries.

Expiry is enforced here, not by Cosmos DB. Per-item ttl is set as a storage reclamation backstop only. Cosmos DB deletes expired items on a best-effort background sweep, so an item can outlive its ttl and still be returned by a read; the store therefore re-checks the stored timestamps on every read and treats a TTL-expired snapshot as absent. Deletion is only ever allowed to fall on a document the store's own rules have already made unreachable, so a reserved document never expires — see Trellis.Asp.Idempotency.Cosmos.CosmosIdempotencyDocument.Ttl. Reservations are removed by AbandonAsync(string, string, string, CancellationToken) or superseded on completion, so the only documents that accumulate are those whose process was killed between reserving and responding.

Reservation timeout depends on host clocks. Takeover compares this instance's clock against a reservedAt written by another instance, so the effective timeout is the configured ReservationTimeout shifted by the clock skew between the two hosts. This does not add a failure mode — the timeout is a liveness bound that already permits taking over a handler that is merely slow rather than dead — but it does move the boundary. Set ReservationTimeout comfortably above the slowest expected handler plus the skew tolerated across the fleet, and keep hosts NTP-synchronised. A single-instance store such as InMemoryIdempotencyStore reads one clock and is not exposed to this. The Retry-After value returned for an in-flight reservation is clamped so that skew cannot push it beyond ReservationTimeout.

Cost. Request-unit charge scales with item size, so an idempotency entry costs roughly what its captured response body costs to write. With MaxResponseBodyBytes at its 1 MiB default a single completion can exceed 100 RU. Lower the cap, or keep large payloads out of the snapshot.

Remarks

Silently ignored if the reservation has since been taken over by another request (because ReservationTimeout elapsed).

Idempotency with CompleteAsync(string, string, string, IdempotencyResponseSnapshot, CancellationToken). IdempotencyMiddleware may invoke this method after CompleteAsync(string, string, string, IdempotencyResponseSnapshot, CancellationToken) partially succeeded — for example, a durable store that wrote the snapshot to the database but then threw during a secondary acknowledgement step. Implementations MUST NOT delete a snapshot that CompleteAsync(string, string, string, IdempotencyResponseSnapshot, CancellationToken) already persisted under the same reservationId; only an in-flight reservation may be released. A safe pattern is to short-circuit when the store-level record already has a non-null snapshot, leaving the completed entry intact for replay.
