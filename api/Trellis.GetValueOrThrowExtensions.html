Production-safe throwing terminal extraction for Result<TValue>, intended for the narrow case where a failure represents a broken invariant the caller cannot act on — typically the persistence DTO → entity rehydration seam, where write-path validation guarantees the row is valid and any TryCreate failure on read indicates database corruption or migration drift.

Remarks

Mirrors GetValueOrThrow(string?) for symmetric ergonomics across the two ROP types: an explicit, named "this throws" contract gated by the verb in the method name, not an ambient property accessor (Result<T>.Value was removed in v3 because the ambient accessor was the primary cause of unsafe value access).

Prefer TryGetValue, Match, Bind, GetValueOrDefault, or destructuring for normal Result-track flow. GetValueOrThrow<TValue>(Result<TValue>, string?) is the escape hatch for trust-boundary crossings where failure means "the world is not as expected" — not for request validation where the caller should surface a typed Error.InvalidInput on the Result track.

Cookbook Recipe 30 covers the persistence-rehydration use case end to end, including the decision criteria for picking this throwing pattern versus a Result<TEntity> end-to-end shape for legacy / corruptible data paths.

GetValueOrThrowAsync<TValue>(Task<Result<TValue>>, string?)

Awaits the task and returns the success value, or throws InvalidOperationException if the result is a failure. This is a terminal operator that exits the Result railway.
