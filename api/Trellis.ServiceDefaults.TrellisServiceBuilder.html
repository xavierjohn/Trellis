Registers the transactional inbox for TContext so an application-owned transport adapter can hand each received integration message to the inbox for exactly-once-per-consumer local processing.

Parameters

configure Action<InboxOptions>

Inbox configuration; ConsumerId is required.

Returns

TrellisServiceBuilder

The same builder for chaining.

Type Parameters

TContext

The consumer's DbContext that owns the inbox table.

Remarks

This slot owns only the service-collection half of the inbox: the IInboxDispatcher, the EF IInboxStore, and its InboxOptions. The InboxMessage table mapping lives on the DbContext and must be wired where the context is configured — call modelBuilder.AddTrellisInbox() in OnModelCreating. This mirrors how UseOutbox<TContext>(Action<OutboxOptions>?) owns the service registration while the table mapping is applied on the context.

The dispatcher records each message under (ConsumerId, MessageId) and fans it out to the registered integration-event handlers inside a single database transaction, so a duplicate delivery is skipped and a handler failure rolls back and lets the transport redeliver. Register the handlers (for example via AddIntegrationEventHandler<TEvent, THandler>() or UseIntegrationEvents()) so the dispatcher has consumers to invoke. ConsumerId is required, so a configure callback that sets it must be supplied.

The registration is order-independent: it adds no Mediator behavior, so calling it before or after UseEntityFrameworkUnitOfWork<TContext>() yields the same canonical pipeline order. Calling this method more than once throws InvalidOperationException; one inbox per composition is supported. The method is annotated RequiresUnreferencedCodeAttribute / RequiresDynamicCodeAttribute because the inbox builds on Trellis.EntityFrameworkCore, which is intentionally opted out of AOT and trim.

UseOutbox<TContext>(Action<OutboxOptions>?)

Registers the transactional-outbox relay for TContext so domain events captured into the outbox table are durably re-dispatched after the transaction commits.

Parameters

configure Action<OutboxOptions>

Optional relay tuning (poll interval, batch size, max attempts).

Returns

TrellisServiceBuilder

The same builder for chaining.

Type Parameters

TContext

The application's DbContext that owns the outbox table.

Remarks

This slot owns only the service-collection half of the outbox: the relay hosted service and its OutboxOptions. The capture interceptor and the OutboxMessage table mapping live on the DbContext and must be wired where the context is configured — call optionsBuilder.AddTrellisOutboxInterceptor() on the options builder and modelBuilder.AddTrellisOutbox() in OnModelCreating. This mirrors how UseEntityFrameworkUnitOfWork<TContext>() owns the service registration while AddTrellisInterceptors is applied on the context.

When the outbox is enabled the capture interceptor clears each aggregate's events inside the commit, so the in-pipeline DomainEventDispatchBehavior observes none and the relay becomes the single, durable dispatch path. Pair this with UseDomainEvents() (or an explicit AddDomainEventDispatch) so the relay has handlers and an IDomainEventPublisher to fan out to. The relay registration is order-independent: it adds a hosted service and does not participate in the Mediator behavior pipeline, so calling it before or after UseEntityFrameworkUnitOfWork<TContext>() yields the same canonical pipeline order.

Calling this method more than once throws InvalidOperationException; one outbox relay per composition is supported. The method is annotated RequiresUnreferencedCodeAttribute / RequiresDynamicCodeAttribute because the outbox builds on Trellis.EntityFrameworkCore, which is intentionally opted out of AOT and trim.

The actor returned when HttpContext is null. Permissions on this actor become the authorization envelope for every mediator command the worker dispatches; scope them as narrowly as the worker requires.

Returns

TrellisServiceBuilder

Remarks

Applied last, AFTER both the HTTP-side actor provider (UseClaimsActorProvider, UseEntraActorProvider, or UseDevelopmentActorProvider) and any UseCachingActorProvider<T>() wrap. The worker wrapper sits on the OUTSIDE so worker-tick lookups never traverse the caching layer (which has no scope to cache against), while HTTP-side lookups flow through caching → inner provider unchanged.

Calling this method requires that an actor provider slot is selected somewhere in the composition — typically via UseClaimsActorProvider, UseEntraActorProvider, UseDevelopmentActorProvider, or UseCachingActorProvider<T>() with a custom provider. Because Apply() records selections and runs them in canonical order, the chain position of UseWorkerActor(...) relative to those selectors does not matter; only that one of them is present. Calling UseWorkerActor twice throws. A hosted-service validator runs at host start and fails fast if any subsequent services.AddScoped<IActorProvider, ...>() registration overwrites the wrapper — background-worker ticks would otherwise stop resolving the configured system actor and would surface the first dispatched command as Error.AuthenticationRequired.
