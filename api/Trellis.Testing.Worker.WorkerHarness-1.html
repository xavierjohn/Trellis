Integration-test harness for a BackgroundService worker. Builds an IHost with a deterministic Microsoft.Extensions.Time.Testing.FakeTimeProvider, a configurable TestActorProvider, and a domain-event capture wired through the Trellis mediator pipeline so tests can advance time, wait for specific events or named tick signals, and assert what the worker emitted.

Remarks

The harness owns hosted-service registration for TWorker. A test that also registers TWorker as an IHostedService in its ConfigureServices(Action<IServiceCollection>) callback will fail fast at CreateAsync(Action<WorkerHarnessOptions>?, CancellationToken) time so the test does not silently run two copies of the worker.

The harness does not register AddDomainEventDispatch(). Worker tests are integration tests of the production composition root — the same registration the worker's production host uses should appear in the test's ConfigureServices(Action<IServiceCollection>) callback. Without it, the open-generic capture handler is registered but the mediator pipeline never publishes events, so Events<TEvent>() would remain empty even when the worker raises events on its aggregates.

Wait timeouts measure real time, not the harness's fake clock — calling Time.Advance(...) does not consume the timeout budget. The fake clock only drives the worker's Task.Delay / PeriodicTimer continuations.

Remarks

For a deterministic alternative, have the worker register its first Delay(TimeSpan, TimeProvider, CancellationToken) BEFORE calling SignalAsync(string, CancellationToken) with a known name (then await the saved delay) and use WaitForTickAsync(string, TimeSpan?, CancellationToken) in the test. The signal must follow the Task.Delay(...) call so the Microsoft.Extensions.Time.Testing.FakeTimeProvider callback is provably registered before the test resumes and advances time.

StartAsync(CancellationToken)

Starts the worker host. On the success path, subsequent calls are no-ops and safe to repeat. If the underlying StartAsync(CancellationToken) throws, the harness drives a best-effort StopAsync(CancellationToken) so any hosted services that started before the failure observe their stop hook, and rethrows the original exception. After a failed start the harness should be discarded — the host's hosted services have already observed a stop transition and re-starting them from the same harness is not a supported scenario.

Remarks

StartAsync(CancellationToken) returns as soon as the BackgroundService's ExecuteAsync(CancellationToken) has been scheduled onto the thread pool, NOT after the worker has registered its first Delay(TimeSpan, TimeProvider, CancellationToken) / PeriodicTimer callback with the harness's Microsoft.Extensions.Time.Testing.FakeTimeProvider. A test that calls await harness.StartAsync(); harness.Time.Advance(period); back-to-back can race the worker: the Advance fires before any callback is registered, the worker then registers Task.Delay(period, FakeTime, ct) with a deadline of (now + period), and the test times out waiting for a tick that needs another Advance(period) to fire.

Two ways to avoid the race:

  1. (Deterministic) Have the worker register its first Delay(TimeSpan, TimeProvider, CancellationToken) BEFORE calling SignalAsync(string, CancellationToken) with a known name (e.g. "ready"), then await the saved delay. The Task.Delay(TimeSpan, TimeProvider, CancellationToken) overload eagerly calls CreateTimer(TimerCallback, object, TimeSpan, TimeSpan) when invoked, so the Microsoft.Extensions.Time.Testing.FakeTimeProvider callback is registered before the signal fires — by the time the test resumes from WaitForTickAsync(string, TimeSpan?, CancellationToken) the callback exists and the subsequent Time.Advance(...) is guaranteed to land on it. Signaling FIRST and registering the delay second would still leave a gap during which the test can advance the clock before any callback is registered.
  2. (Lazy) Call SettleAsync(TimeSpan?, CancellationToken) after StartAsync. This is a real-time yield so the worker's first scheduling turn lands before the test advances the clock. Convenient for one-off tests but adds wall-clock latency.
